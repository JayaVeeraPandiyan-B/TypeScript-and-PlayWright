# How did you do it? (Technical approach)

Framework setup: I set up the Playwright + TypeScript project using Node.js and npm. I created a structured folder layout — pages (POM classes), tests, utils, fixtures, and config. Each page of the application had its own class with locators and reusable action methods.

Cross-browser execution: Using playwright.config.ts, I configured projects for Chromium, Firefox, and WebKit so tests run in parallel across all three browsers in a single command.

API testing: I used Playwright's built-in request context for API calls within the same test run. For standalone API validation, I maintained Postman collections with environment variables for different test environments — dev, staging, UAT.

Data validation: I connected to MySQL using the mysql2 npm package and to Snowflake using the snowflake-sdk. My utility function would run a query, fetch the expected value, and then my test would assert it against what Playwright scraped from the Power BI dashboard.

AI acceleration: I used GitHub Copilot inside VS Code to auto-suggest POM methods, generate repetitive test blocks, and refactor duplicated code. MCP was used to connect AI agents to our test toolchain for smarter test orchestration.

Reporting + CI: Allure Reports were integrated with the test runner. On every Jenkins pipeline run, a fresh Allure report was generated and published, so stakeholders could see the latest results without needing access to the codebase.

# What difficulties did you face?

1. Dynamic UI in Power BI dashboards: Power BI renders content as SVG and canvas elements, which standard Playwright locators struggle with. I had to write custom JavaScript evaluation scripts inside Playwright to extract text from SVG nodes and canvas layers. It took several days of research, but once the utility was built, it became reusable across all dashboard tests.

2. Flaky tests in cross-browser runs: Some tests that passed perfectly on Chromium would fail intermittently on WebKit due to timing differences. I resolved this by implementing smart waits — waitForSelector and waitForResponse — instead of fixed sleep delays, which made tests much more stable.

3. Snowflake query latency: When fetching data from Snowflake for validation, the queries sometimes took 10–15 seconds, causing test timeouts. I fixed this by increasing the timeout threshold for data-validation tests specifically, and also optimised my SQL queries to reduce execution time.

4. Onboarding team members mid-project: When two junior members joined, they were unfamiliar with Playwright and TypeScript. I created a quick-start guide, held weekly knowledge-sharing sessions, and reviewed their pull requests, which brought them up to speed within three weeks.

5. Keeping up with AI tooling: MCP and AI agents were relatively new, and there was limited documentation. I invested personal time exploring GitHub repos, community forums, and official docs to build working integrations.

# How long does execution take in CI/CD pipeline?

In our Jenkins-based CI/CD pipeline, the full Playwright test suite of 150+ tests runs in approximately 20 to 30 minutes end-to-end, including environment setup, parallel test execution across browsers, and Allure report generation.

Pipeline stages breakdown:

• Checkout + npm install: 2–3 minutes
• Environment config (env vars, test data setup): 1–2 minutes
• Parallel test execution (3 browsers simultaneously): 12–18 minutes
• Allure report generation + publish: 2–3 minutes
• Notification (email/Slack on failure): less than 1 minute

Smoke suite (critical path only, ~30 tests): Runs in 5–8 minutes and is triggered on every code merge to the main branch.

Full regression suite (150+ tests): Runs nightly as a scheduled Jenkins job and on every sprint release candidate build.

The Allure dashboard is published after every run, so the QA team and project leads can immediately see pass/fail status without accessing Jenkins directly.
