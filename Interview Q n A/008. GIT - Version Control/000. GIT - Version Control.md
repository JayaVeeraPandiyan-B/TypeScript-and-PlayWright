
# GIT / VERSION CONTROL – Interview Answers

**1. What is Git and why is it used?**

* Git is a distributed version control system used to track code changes during software development.

* It helps multiple developers work on the same project without overwriting each other’s changes.

* Why Git is used:

  * Tracks code history
  * Supports collaboration among teams
  * Helps create branches for feature development
  * Allows rollback to previous versions
  * Integrates with CI/CD tools like Jenkins, GitHub Actions, Azure DevOps, etc.

* Interview Answer: > Git is a distributed version control tool used to manage source code changes. It helps developers track modifications, collaborate with teams, maintain code history, and support branching and merging activities efficiently.

---

**2. Explain Git workflow and stages of commit.**

* Git Workflow:

  1. Developer modifies code in working directory
  2. Changes are added to staging area using `git add`
  3. Changes are committed to local repository using `git commit`
  4. Code is pushed to remote repository using `git push`

* Stages in Git:

  * **Working Directory** → Actual files being modified
  * **Staging Area** → Temporary area before commit
  * **Local Repository** → Stores committed code locally
  * **Remote Repository** → Shared repository like GitHub/GitLab

* Common Flow:

```bash
git add .
git commit -m "Added login automation"
git push origin branch_name
```

* Interview Answer: > In Git workflow, code changes are first made in the working directory, then added to the staging area using git add. After validation, the changes are committed to the local repository using git commit and finally pushed to the remote repository using git push.

**3. Common Git commands used in projects.**

| Command         | Purpose                     |
| --------------- | --------------------------- |
| `git clone`     | Copy repository from remote |
| `git status`    | Check modified files        |
| `git add .`     | Add files to staging area   |
| `git commit -m` | Commit changes              |
| `git pull`      | Fetch latest changes        |
| `git push`      | Push code to remote         |
| `git branch`    | View/create branches        |
| `git checkout`  | Switch branches             |
| `git merge`     | Merge branches              |
| `git stash`     | Temporarily save changes    |
| `git log`       | View commit history         |
| `git revert`    | Undo committed changes      |

* Interview Answer: > Common Git commands used in projects include git clone, git pull, git add, git commit, git push, git checkout, git merge, git stash, and git log. These commands help in code management, collaboration, and version tracking.

**4. Difference between git clone, pull, patch, merge, rebase, and stash.**

| Command      | Description                                                     |
| ------------ | --------------------------------------------------------------- |
| `git clone`  | Creates local copy of remote repository                         |
| `git pull`   | Downloads latest changes and merges automatically               |
| `git patch`  | Shares code changes as patch files                              |
| `git merge`  | Combines changes from one branch to another                     |
| `git rebase` | Moves branch commits on top of another branch for clean history |
| `git stash`  | Temporarily stores uncommitted changes                          |

* Interview Answer: > Git clone is used to copy a repository locally. Git pull fetches and merges latest remote changes. Merge combines branches, while rebase rewrites commit history for cleaner tracking. Stash temporarily saves unfinished work, and patch is used to share code changes without directly merging code.

**5. How do you resolve merge conflicts?**

* Steps:

 1. Pull latest changes
 2. Git highlights conflicting files
 3. Open files and identify conflict markers:
```bash
<<<<<<< HEAD
Current code
=======
Incoming code
>>>>>>> branch_name
```
  4. Manually fix the conflict
  5. Save the file
  6. Add and commit changes

* Commands:

```bash
git add .
git commit -m "Resolved merge conflict"
```

* Interview Answer: > Merge conflicts occur when two developers modify the same lines of code. I resolve conflicts by reviewing the conflicting sections manually, keeping the correct changes, removing conflict markers, and then committing the resolved code.

**6. What is .gitignore and why is it important?**

* `.gitignore` is a file used to exclude unnecessary files from Git tracking.

* Common files ignored:

  * Log files
  * Build folders
  * Temporary files
  * IDE configuration files
  * Sensitive data like passwords

* Example:

```bash
*.log
target/
node_modules/
```

* Importance:

  * Prevents unwanted files from entering repository
  * Improves repository cleanliness
  * Protects sensitive information

* Interview Answer: > .gitignore is used to prevent unnecessary or sensitive files from being tracked by Git. It helps keep the repository clean and avoids committing temporary files, logs, build files, and confidential data.

**7. How do you revert changes from remote repositories?**

* To discard local changes:

```bash
git checkout -- filename
```

* To revert committed changes:

```bash
git revert commit_id
```

* To reset completely:

```bash
git reset --hard HEAD
```

* To sync with remote:

```bash
git fetch
git reset --hard origin/main
```

* Interview Answer: > To revert changes, I use git revert for committed changes because it safely creates a new commit that undoes previous changes. If required, I use git reset carefully to match the remote repository state.

**8. How do you validate latest code updates after commit?**

* Validation Steps:

  * Pull latest code
  * Check commit history using:

```bash
git log
```

* Compare changes:

```bash
git diff
```

  * Verify commit in remote repository
  * Run automation test suite/build validation
  * Check CI/CD pipeline status

* Interview Answer: > After committing code, I validate updates by checking git log, verifying changed files using git diff, pulling latest changes, and executing automation test cases or CI/CD pipelines to ensure no issues were introduced.

**9. Explain branching strategies in automation projects.**

* Common Branching Strategy:

  * `main/master` → Production-ready code
  * `develop` → Integration branch
  * `feature branches` → Individual feature development
  * `release branch` → Pre-production testing
  * `hotfix branch` → Urgent production fixes

* Example:

```bash
feature/login-automation
feature/api-framework
```

* Benefits:

  * Parallel development
  * Easy code review
  * Reduced conflicts
  * Stable production code

* Interview Answer: > In automation projects, branching strategies help manage parallel development. Usually, we use feature branches for new automation scripts, develop branch for integration testing, and main branch for stable production-ready code. This improves collaboration and minimizes code conflicts.

**10. Difference between SVN and Git.**

| SVN                         | Git                         |
| --------------------------- | --------------------------- |
| Centralized version control | Distributed version control |
| Requires server connection  | Can work offline            |
| Slower branching            | Faster branching            |
| Single central repository   | Multiple local repositories |
| Less flexible               | Highly flexible             |

* Interview Answer: > SVN is a centralized version control system, whereas Git is distributed. Git provides better branching, offline work support, faster performance, and improved collaboration compared to SVN. That is why most modern projects prefer Git.
