
# Practical / Scenario-Based API Interview Answers

**1. How would you test an API if no documentation is available?**

* If no API documentation is available, I would follow these steps:

  * Step 1 — Understand Application Flow

    * Observe frontend network calls using browser DevTools
    * Identify endpoints, methods, headers, and payloads

  * Step 2 — Analyze Existing Requests

    * Using:

      * Chrome Network tab
      * Postman proxy
      * Logs

  * Step 3 — Identify API Details

    * Validate:

      * HTTP methods
      * Request payloads
      * Authentication
      * Response structure

  * Step 4 — Perform Exploratory Testing

    * Test:

      * Positive scenarios
      * Negative scenarios
      * Invalid inputs
      * Boundary conditions

  * Step 5 — Validate Backend Behavior

    * Verify:

      * Database changes
      * Logs
      * Response codes
      * Business rules

* Tools used:

  * Postman
  * REST Assured
  * Browser DevTools
  * SQL queries

---

**2. How do you identify whether an issue is from frontend, backend, or database?**

* I isolate the issue layer by layer.

  * Frontend Issue, If:

    * API works correctly in Postman
    * UI displays incorrect data
    * UI validation issue exists

  * Then issue is likely frontend-related.

---

  * Backend/API Issue, If:

    * Incorrect response returned
    * Wrong status code
    * Business logic failure

  * Then issue is backend-related.

---

  * Database Issue, If:

    * API succeeds but DB not updated
    * Incorrect DB records
    * Stored procedure failure

* Then issue is database-related.

  * Approach:

    * Validate UI
    * Validate API response
    * Validate DB data

---

* After POST API execution, I validate:

  * Status code
  * Response body
  * Response headers
  * Generated ID
  * Database entry
  * Business rules
  * Response schema
  * Response time

* Example validations:

  * 201 Created
  * Resource ID generated
  * Correct data stored in DB

**4. How do you validate database changes after API execution?**

* Steps:

  * Execute API request
  * Extract unique identifier
  * Run SQL query
  * Compare API response with DB values

* Example:

```sql id="8jk18m"
SELECT * FROM users WHERE id=101;
```

* Validations:

  * Record inserted
  * Updated values correct
  * Deleted records removed

* Tools:

  * SQL Developer
  * DBeaver
  * JDBC connections

**5. How do you handle expired tokens in automation?**

* Approach:

  * Detect token expiration response (401)
  * Automatically regenerate token
  * Store new token
  * Retry failed request

* Example:

```java id="xv2eqm"
if(statusCode == 401){
   generateNewToken();
}
```

* Best practice: Centralize token generation utility

**7. How do you validate nested JSON responses?**

* Example response:

```json id="13km0f"
{
  "user": {
    "name": "John",
    "address": {
      "city": "Chennai"
    }
  }
}
```

```java id="5c4a9h"
body("user.address.city", equalTo("Chennai"));
```

* Validations:

  * Nested objects
  * Arrays
  * Data types
  * Null values

**9. How do you handle flaky API tests?**

* Flaky tests produce inconsistent results.

  * Approach:

    * Identify unstable dependencies
    * Use proper waits/retries
    * Avoid hardcoded data
    * Improve environment stability
    * Isolate test data
    * Mock unstable services

  * Common causes:

    * Network delays
    * Shared test data
    * Token expiration
    * Environment instability

---

    * Compare old vs new behavior

  * Coverage:

    * CRUD operations

    * Error handling

  * Tools:

    * Postman
    * REST Assured

**13. How do you troubleshoot intermittent API failures?**

* Approach:

  * Check logs
  * Verify server health
  * Analyze network latency
  * Validate DB connections
  * Retry manually
  * Check timeout configurations

* Possible causes:

  * Network instability
  * Server overload
  * Dependency failures
  * Race conditions

* Also analyze:

  * Failure patterns
  * Specific environments
  * Time-based occurrences

**14. How do you validate API backward compatibility after version changes?**

* Validations:

  * Old clients should continue working
  * Existing response fields should remain unchanged
  * Deprecated APIs should still function
  * Response schema compatibility
  * Existing automation suite should pass

* Approach:

  * Compare v1 and v2 responses
  * Execute regression suite
  * Perform contract testing

* Example:

```text id="emlf1p"
/api/v1/users
/api/v2/users
```

* Goal: Avoid breaking existing integrations.
